# LeadFix Conversion Audit Method v1

Методология для AI-аудита лендингов: 6 зон потери заявки, 108 проверяемых критериев, scoring 0-100, единый формат проблем и приоритетный план внедрения.

## 1. Позиционирование

Коротко для сайта:

> LeadFix проверяет лендинг по собственной CRO-методологии из 100+ критериев и показывает, какие проблемы мешают заявкам, что исправить первым и какой эффект ожидать.

Внутреннее описание:

LeadFix не оценивает "красоту сайта". Он ищет потери заявки: где пользователь не понял предложение, не поверил, не увидел следующий шаг, столкнулся с трением в форме, потерял фокус в структуре или не смог удобно оставить заявку с мобильного.

Главный продуктовый результат аудита:

- общий LeadFix Score от 0 до 100;
- оценки по 6 зонам;
- список проблем с evidence;
- приоритеты внедрения;
- примеры улучшенных формулировок;
- ограничения анализа и пункты для дополнительной проверки.

## 2. Архитектура методологии

| Зона | Что проверяет | Вес |
|---|---|---:|
| Оффер | Понимает ли посетитель, что ему предлагают и зачем оставлять заявку | 22% |
| CTA | Видит ли посетитель понятный следующий шаг | 18% |
| Доверие | Есть ли причины поверить обещаниям сайта | 18% |
| Формы и заявки | Насколько легко и безопасно оставить заявку | 14% |
| Структура страницы | Ведёт ли страница к заявке без потери фокуса | 16% |
| Мобильная версия | Работает ли путь к заявке на мобильном трафике | 12% |

Для лендингов с 70%+ мобильного трафика из Яндекс Директа:

| Зона | Вес |
|---|---:|
| Оффер | 20% |
| CTA | 18% |
| Доверие | 16% |
| Формы и заявки | 15% |
| Структура страницы | 13% |
| Мобильная версия | 18% |

## 3. Scoring

Каждая зона получает оценку 0-10.

Общий балл:

```text
overall_score = sum(category_score * category_weight)
```

Где `category_score` нормализуется к 100: оценка 8/10 при весе 22% даёт 17.6 балла.

Интерпретация:

| Балл | Вывод |
|---:|---|
| 0-39 | Лендинг системно теряет заявки. Нужна переработка оффера, структуры или формы. |
| 40-59 | Есть базовая работоспособность, но несколько критичных барьеров мешают конверсии. |
| 60-74 | Лендинг можно улучшить точечными правками и усилением аргументов. |
| 75-89 | Хорошая база. Работать через A/B-гипотезы и повышение доверия. |
| 90-100 | Сильная страница. Дальше нужны аналитика, тесты и сегментация трафика. |

Минимальные пороги качества:

- оффер ниже 6/10: нельзя считать аудит положительным, даже если общий балл высокий;
- CTA ниже 6/10: обязательно попадает в top-priority;
- формы ниже 5/10: помечать как риск потери заявок;
- mobile ниже 6/10 при мобильном трафике: критичная проблема.

Уверенность AI:

| Confidence | Значение |
|---:|---|
| 0.90-1.00 | Вывод явно подтверждён HTML, текстом или скриншотом |
| 0.70-0.89 | Вывод вероятен, но нужен контекст ниши или трафика |
| 0.50-0.69 | Гипотеза, нужна дополнительная проверка |
| <0.50 | Не использовать как рекомендацию, только как вопрос к эксперту |

## 4. Шкала 0-10 по зонам

Оффер:

- 0-2: непонятно, что предлагается;
- 3-4: понятно направление, но нет результата, аудитории или выгоды;
- 5-6: есть базовый оффер, но слабая конкретика;
- 7-8: понятный оффер с выгодой и релевантностью;
- 9-10: конкретный, дифференцированный оффер с сильной причиной обратиться.

CTA:

- 0-2: нет явного целевого действия;
- 3-4: CTA есть, но формулировка слабая или плохо заметна;
- 5-6: основной CTA понятен, но не поддержан по странице;
- 7-8: CTA заметен, повторяется и соответствует этапу принятия решения;
- 9-10: CTA снимает неопределённость и ведёт к заявке без трения.

Доверие:

- 0-2: нет доказательств, контактов, кейсов или подтверждений;
- 3-4: есть общие заявления без фактов;
- 5-6: есть часть trust-сигналов, но они слабые или неполные;
- 7-8: доверие подтверждено кейсами, цифрами, отзывами, лицами, гарантиями;
- 9-10: доказательства конкретны, релевантны нише и встроены рядом с решением.

Формы и заявки:

- 0-2: форма отсутствует, не работает или непонятна;
- 3-4: форма есть, но слишком сложная или пугающая;
- 5-6: заявку можно оставить, но есть лишние поля или слабое пояснение;
- 7-8: форма короткая, понятная, с ожиданием следующего шага;
- 9-10: форма минимизирует риск, поддержана microcopy и альтернативными контактами.

Структура страницы:

- 0-2: блоки хаотичны, путь к заявке не считывается;
- 3-4: есть базовая структура, но логика убеждения проваливается;
- 5-6: последовательность понятна, но есть лишние или слабые блоки;
- 7-8: страница ведёт от оффера к доверию, аргументам и заявке;
- 9-10: каждый блок работает на решение, возражения и действие.

Мобильная версия:

- 0-2: мобильная версия мешает пользоваться сайтом;
- 3-4: основные элементы видны, но есть серьёзные UX-проблемы;
- 5-6: мобильный путь рабочий, но слабая читаемость, CTA или форма;
- 7-8: удобно читать, нажимать и отправлять заявку;
- 9-10: мобильный сценарий оптимизирован под быстрый вход из рекламы.

## 5. Чек-листы: 108 критериев

Критерий считается проверяемым, если AI может сослаться на текст, HTML-элемент, скриншот, порядок блоков или отсутствие нужного элемента.

### 5.1 Оффер

1. На первом экране понятно, какой продукт или услуга предлагается.
2. В заголовке или подзаголовке есть конкретный результат для клиента.
3. Указано, для кого предназначено предложение.
4. Есть связь с болью или задачей целевой аудитории.
5. Оффер не состоит из общих слов вроде "эффективные решения" без расшифровки.
6. Пользователь понимает, что произойдёт после обращения.
7. Указаны сроки, диапазон результата, формат работы или понятная единица ценности.
8. Есть отличие от типовых конкурентов.
9. Первый экран отвечает на вопрос "почему оставить заявку здесь".
10. Текст оффера совпадает с вероятным намерением рекламного трафика.
11. Нет конфликта между заголовком, подзаголовком и CTA.
12. Оффер можно понять без прокрутки.
13. Визуал первого экрана помогает понять предложение, а не просто украшает.
14. Нет нескольких равнозначных офферов, конкурирующих между собой.
15. Есть конкретика по услуге, продукту, аудитории или ситуации применения.
16. Формулировки написаны языком клиента, а не внутренним жаргоном компании.
17. Если цена или выгода важны для выбора, они не спрятаны слишком глубоко.
18. Оффер не обещает недоказуемый результат без подтверждений.

### 5.2 CTA

1. На первом экране есть основной CTA.
2. CTA визуально заметен на фоне остальных элементов.
3. Текст CTA описывает действие, а не абстрактное "Отправить".
4. CTA соответствует офферу.
5. Основной CTA повторяется после ключевых смысловых блоков.
6. Рядом с CTA понятно, что пользователь получит после клика.
7. Есть мягкий CTA для холодного трафика, если заявка требует высокого доверия.
8. На странице нет конкуренции нескольких равнозначных целевых действий.
9. Кнопки одинакового назначения имеют согласованную формулировку.
10. CTA не уводит пользователя в нерелевантный сценарий.
11. Кнопки выглядят кликабельными.
12. Важные CTA не скрыты внутри длинного текста.
13. CTA расположен рядом с аргументом или доказательством, которое усиливает действие.
14. Для срочного действия есть честная причина действовать сейчас.
15. CTA не обещает то, чего нет в следующем шаге.
16. После клика путь к заявке очевиден.
17. Для мобильной версии CTA доступен без лишней прокрутки.
18. CTA не перегружен длинным текстом.

### 5.3 Доверие

1. На странице есть реальные контакты компании.
2. Есть юридическая информация или реквизиты, если ниша требует доверия.
3. Есть отзывы, кейсы, клиенты или примеры работ.
4. Кейсы содержат конкретику: задача, процесс, результат.
5. Цифры и обещания подтверждены контекстом.
6. Есть лица, команда, экспертность или авторство.
7. Присутствуют гарантии, условия или снижение риска.
8. Есть ответы на типовые возражения.
9. Доверительные блоки расположены до или рядом с важными CTA.
10. Отзывы не выглядят как анонимные шаблоны без деталей.
11. Визуальный стиль не снижает ощущение надёжности.
12. Нет противоречий между обещаниями и доказательствами.
13. Есть подтверждение опыта в конкретной нише или типе задач.
14. Указаны понятные условия оплаты, сроков или начала работы.
15. Есть политика обработки персональных данных для формы.
16. Сайт не создаёт ощущение скрытой компании без ответственных лиц.
17. Доказательства соответствуют уровню риска сделки.
18. Нет необоснованных "лидер рынка", "№1", "лучший" без подтверждений.

### 5.4 Формы и заявки

1. Форма или способ заявки доступны на странице.
2. Количество полей соответствует ценности оффера.
3. Обязательные поля визуально понятны.
4. Поля имеют понятные labels или placeholder.
5. Не запрашиваются лишние данные до возникновения доверия.
6. Есть согласие на обработку персональных данных.
7. Ошибки заполнения понятны пользователю.
8. После отправки понятно, что заявка принята.
9. Рядом с формой указано, что произойдёт дальше.
10. Есть альтернативный канал связи: телефон, мессенджер или email.
11. Кликабельны телефон и мессенджеры.
12. Форма не спрятана слишком глубоко.
13. Форма не перегружена юридическим или техническим текстом.
14. Кнопка формы соответствует обещанию рядом с формой.
15. На мобильном поля удобно нажимать и заполнять.
16. Форма не ломает доверие просьбой о чувствительных данных без причины.
17. Есть защита от спама без лишнего трения для пользователя.
18. Форма не конфликтует с виджетами, попапами или sticky-элементами.

### 5.5 Структура страницы

1. Первый экран быстро объясняет предложение.
2. После первого экрана идут аргументы, а не случайные декоративные блоки.
3. Страница имеет один главный сценарий конверсии.
4. Блоки расположены в логике: оффер, выгоды, доказательства, процесс, возражения, заявка.
5. Пользователь видит достаточно информации до просьбы оставить заявку.
6. Нет длинных участков без CTA.
7. Есть блок, объясняющий процесс работы или следующий шаг.
8. Есть блок с ответами на возражения.
9. Есть FAQ, если продукт сложный или рискованный.
10. Текст разделён на считываемые смысловые блоки.
11. Важные аргументы не спрятаны ниже второстепенных деталей.
12. Визуальная иерархия помогает сканировать страницу.
13. Нет лишних секций, не влияющих на решение.
14. Повторы усиливают мысль, а не создают шум.
15. Страница не заставляет пользователя самому собирать смысл из разрозненных фраз.
16. Блок цены или условий расположен там, где он нужен для решения.
17. Навигация не уводит из конверсионного сценария.
18. Финальный блок повторяет ценность и даёт понятный CTA.

### 5.6 Мобильная версия

1. Первый экран на мобильном показывает суть предложения без чрезмерной прокрутки.
2. Заголовок читается без переноса в нечитаемую "лесенку".
3. Основной CTA виден или быстро доступен.
4. Кнопки имеют достаточный размер для нажатия.
5. Текст читается без увеличения.
6. Форма помещается и заполняется без горизонтального скролла.
7. Sticky-элементы не перекрывают CTA, форму или текст.
8. Попапы не блокируют сценарий заявки.
9. Изображения не съедают первый экран без пользы.
10. Телефон и мессенджеры кликабельны.
11. Блоки идут в мобильной логике, а не просто сжаты с десктопа.
12. Нет горизонтальной прокрутки.
13. Важные proof-сигналы доступны до формы.
14. Поля формы вызывают правильную мобильную клавиатуру.
15. Скорость и вес страницы не создают очевидного риска отказа.
16. Тап по CTA ведёт к форме, контакту или понятному действию.
17. На мобильном не теряются цены, условия или важные ограничения.
18. Отступы и размеры не создают случайных нажатий.

## 6. Типология проблем

| Тип | Смысл | Частые зоны |
|---|---|---|
| unclear_offer | Пользователь не понимает предложение | Оффер, структура |
| weak_value | Нет сильной причины оставить заявку | Оффер, CTA |
| trust_gap | Не хватает доказательств и надёжности | Доверие |
| friction | Сложно оставить заявку | Формы, mobile |
| weak_motivation | Нет причины действовать сейчас | CTA, оффер |
| overload | Слишком много текста, вариантов или действий | Структура, mobile |
| technical_risk | Что-то может ломать путь заявки | Формы, mobile |
| traffic_mismatch | Страница не совпадает с ожиданием трафика | Оффер, структура |
| focus_loss | Лендинг рассеивает внимание | CTA, структура |
| missing_evidence | Обещания не подтверждены фактами | Доверие, оффер |

## 7. Issue object

```json
{
  "id": "issue_001",
  "category": "offer",
  "criterion_id": "offer_002",
  "problem_type": "weak_value",
  "problem": "На первом экране не указана конкретная выгода для клиента.",
  "evidence": "В заголовке используется общая формулировка без результата, срока или измеримой пользы.",
  "impact": 5,
  "complexity": 1,
  "priority_score": 4.5,
  "severity": "critical",
  "confidence": 0.86,
  "why_it_affects_conversion": "Посетитель не понимает, зачем оставлять заявку именно здесь, и сравнивает сайт с конкурентами только по общему впечатлению.",
  "recommendation": "Переписать первый экран через конкретный результат, аудиторию и следующий шаг.",
  "example": "Получите 15-30 заявок в месяц с лендинга под Яндекс Директ без полной переделки сайта.",
  "implementation_hint": "Заменить H1 и подзаголовок, затем согласовать текст первой CTA-кнопки с новым обещанием.",
  "expected_result": "Быстрее считывается ценность предложения, повышается вероятность клика по первому CTA.",
  "needs_human_review": false
}
```

Правила полей:

- `problem` - конкретная проблема, не оценочное мнение.
- `evidence` - ссылка на видимый факт: текст, элемент, отсутствие элемента, экран.
- `impact` - влияние на заявки от 1 до 5.
- `complexity` - сложность исправления от 1 до 5.
- `priority_score` - формула ниже.
- `confidence` - уверенность AI, не критичность.
- `needs_human_review` - true, если нужен доступ к аналитике, CRM, рекламным объявлениям или техническому тесту.

## 8. Приоритизация

Impact:

- 5 - влияет на понимание оффера, первый CTA, форму или мобильный путь;
- 4 - заметно снижает доверие или мотивацию;
- 3 - ухудшает восприятие, но не блокирует заявку;
- 2 - локальная UX/текстовая проблема;
- 1 - косметика.

Complexity:

- 1 - заменить текст, кнопку, подпись, порядок одного элемента;
- 2 - изменить блок;
- 3 - перестроить несколько блоков;
- 4 - переработать дизайн или сценарий;
- 5 - разработка, интеграции, аналитика, backend.

Формула:

```text
priority_score = (impact * confidence * severity_multiplier) / complexity
```

Severity multiplier:

- critical: 1.25;
- high: 1.1;
- medium: 1.0;
- low: 0.8.

Классы рекомендаций:

| Класс | Условие |
|---|---|
| Quick Wins | impact >= 4 и complexity <= 2 |
| High Impact Fixes | impact >= 4 и complexity >= 3 |
| Structural Improvements | затрагивает структуру, оффер или сценарий нескольких блоков |
| Later / Nice to Have | impact <= 2 |
| Needs Human Review | confidence < 0.7 или нужны данные вне страницы |

## 9. Формат рекомендации для клиента

Каждая рекомендация в отчёте пишется по шаблону:

1. Проблема.
2. Почему это влияет на заявки.
3. Что исправить.
4. Как именно исправить.
5. Пример улучшения.
6. Ожидаемый эффект.
7. Приоритет.

Запрещены формулировки:

- "улучшить оффер";
- "сделать красивее";
- "добавить доверия";
- "оптимизировать CTA";
- "улучшить UX".

Допустимый формат:

> На первом экране не указано, какой конкретный результат получит клиент после обращения. Сейчас заголовок говорит о категории услуги, но не даёт причины оставить заявку. Лучше заменить его на обещание с результатом и аудиторией: "Запустим лендинг под Яндекс Директ за 7 дней, чтобы вы получали больше заявок из рекламы". Приоритет: Quick Win.

## 11. MVP workflow

MVP должен быть модульным, но не мультиагентным.

1. Data Collector
   - вход: URL;
   - собирает: HTML, text extraction, H1-H3, CTA, формы, ссылки, desktop/mobile screenshots;
   - выход: `page_snapshot`.

2. CRO Analyzer
   - вход: `page_snapshot`;
   - проверяет 6 зон по критериям;
   - выход: raw category scores и raw issues.

3. Issue Normalizer
   - приводит проблемы к `issue object`;
   - удаляет дубли;
   - требует evidence для каждой проблемы.

4. Priority Engine
   - считает impact, complexity, severity, confidence, priority_score;
   - раскладывает issues по классам внедрения.

5. Report Generator
   - превращает JSON в клиентский отчёт;
   - пишет языком владельца бизнеса.

6. Quality Reviewer
   - проверяет воду, противоречия, отсутствие evidence, завышенную критичность, выдуманные факты.

## 12. Production roadmap

Production-версия может перейти к агентам:

| Агент | Роль |
|---|---|
| Extractor Agent | Собирает HTML, текст, скриншоты, структуру, формы |
| Offer Agent | Проверяет оффер, первый экран, соответствие трафику |
| CTA Agent | Проверяет призывы к действию и путь клика |
| Trust Agent | Проверяет доказательства, риски, юридические сигналы |
| Form Agent | Проверяет формы, поля, отправку, microcopy |
| Structure Agent | Проверяет логику блоков и фокус страницы |
| Mobile Agent | Проверяет мобильный сценарий заявки |
| Prioritizer Agent | Нормализует impact, complexity, severity |
| Editor Agent | Переписывает формулировки и примеры улучшений |
| Critic Agent | Ищет слабые выводы, воду и противоречия |

Для MVP мультиагенты не нужны: они увеличат стоимость, задержку и количество конфликтов. Достаточно одного orchestrator-пайплайна с жёсткими JSON-схемами и Quality Reviewer на выходе.

## 13. Quality Reviewer

Проверка перед выдачей отчёта:

- у каждой проблемы есть evidence;
- проблема связана с конверсией, а не личным вкусом;
- нет советов без конкретного действия;
- нет противоречий между score и severity;
- нет выдуманных данных по аналитике, трафику, CRM или A/B-тестам;
- confidence ниже 0.7 отправляет пункт в human review;
- quick wins действительно имеют низкую сложность;
- рекомендации понятны владельцу бизнеса;
- топ-5 проблем не дублируют одну и ту же мысль;
- ограничения анализа явно указаны.

JSON quality review:

```json
{
  "passed": true,
  "score": 92,
  "failed_checks": [],
  "warnings": [
    {
      "type": "low_confidence",
      "message": "Вывод о соответствии рекламному трафику требует данных из объявлений.",
      "issue_id": "issue_007"
    }
  ],
  "required_fixes_before_delivery": []
}
```

## 14. Ограничения анализа

LeadFix должен честно указывать ограничения:

- анализ HTML и скриншотов не равен A/B-тесту;
- без Метрики, CRM и рекламных объявлений нельзя точно оценить вклад каждой проблемы в потери заявок;
- техническая отправка форм требует отдельного теста;
- соответствие рекламному запросу требует данных по кампаниям;
- мобильная оценка зависит от viewport и качества скриншота;
- AI не должен утверждать факты, которых нет в исходных данных.

Формулировка для отчёта:

> Анализ показывает вероятные причины потери заявок по структуре, тексту, формам и мобильному сценарию. Это не заменяет A/B-тест и данные аналитики, но даёт приоритетный список правок, которые можно внедрить до более дорогой переработки сайта.
